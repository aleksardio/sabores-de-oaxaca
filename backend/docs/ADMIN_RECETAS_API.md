# Administración de recetas

Todas las rutas requieren JWT válido y rol `ADMIN`. `GET /api/v1/admin/recetas` acepta `texto` (título o autor, máximo 100 caracteres), `estado` (`BORRADOR`, `PENDIENTE`, `PUBLICADA`, `RECHAZADA`, `ARCHIVADA`), `baja` (`true`/`false`), `pagina` (desde cero) y `tamano` (1–100, predeterminado 20). La respuesta contiene `contenido`, `pagina`, `tamano`, `totalElementos`, `totalPaginas`; orden por ID ascendente. Cada fila incluye `id`, `titulo`, `autor`, `estado`, `eliminadoEn`, `creadoEn` y `version`. `GET /api/v1/admin/recetas/{id}` devuelve el mismo detalle administrativo.

`POST /api/v1/admin/recetas/{id}/baja` y `/restaurar` requieren `If-Match: "version"` y JSON `{"detalle":"justificación"}` no blanco, hasta 1000 caracteres. Devuelven el detalle actualizado. `400`: datos o versión inválidos; `401`: sin sesión; `403`: sin ADMIN; `404`: receta inexistente; `409`: versión obsoleta o baja incompatible. La baja conserva estado y asociaciones; la restauración conserva estado salvo `PUBLICADA`, que pasa a `PENDIENTE` y requiere nueva aprobación. El cambio y `auditoria_administrativa` son transaccionales; la restauración de una publicación añade `RESTAURAR_BAJA` a `auditoria_moderacion`. No se eliminan favoritos, reportes, asociaciones ni archivos. Los reportes pendientes no se resuelven automáticamente mediante esta operación administrativa.

Antes de desplegar, validar los filtros, auditoría, concurrencia, visibilidad pública y recuperación en MySQL 8 aislado. No hay migración nueva. Tras revisión y aprobación, respaldar base y archivos, compilar backend y frontend y publicar con el procedimiento habitual; no cargar datos demo en producción. Ante errores, revertir la versión de aplicación según el procedimiento operativo, sin borrar registros ni modificar migraciones.
